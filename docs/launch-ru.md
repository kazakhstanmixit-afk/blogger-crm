# MIXIT Connect — запуск пилота

Приложение: существующий адрес Blogger CRM + `/discovery/`. Общая база и существующие учётные записи CRM. Работает на компьютере и iPhone. Это PWA, не отдельная программа из App Store.

## Согласованный рабочий цикл

Apify → проверка дублей → отбор → стандартное обращение Instagram → ответ и прайс → предложение товара и доплаты → решение тимлида → отправка предложения → согласие блогера → связанная интеграция Barter Box → WhatsApp → самовыкуп или доставка → Blogery Audit → видео/GATE/правки → публикация → оплата и аналитика.

Наличие кода отдельных компонентов не означает, что вся цепочка уже подключена на рабочих сервисах.

### Условия и товары

В пилоте менеджер создаёт предложение из карточки блогера, указывает исходный прайс, товар/набор, количество, себестоимость, внутреннюю наценку, доплату, доставку и объём размещения. Наценка задаётся явно: например, 4–5 тысяч тенге, но не обязательное правило для каждого товара. Оценка с наценкой не объявляется ценой Kaspi. Блогеру можно назвать только товар и денежную доплату.

Вкладка «Условия / согласование» показывает экономику и точный текст. Тимлид одобряет, отклоняет или просит изменения. Из одобренного предложения менеджер создаёт обращение и отдельно ставит его роботу. Одобрение само по себе не отправляет сообщение. Исправленное предложение подаётся новой записью; история решения сохраняется.

Права тимлида: существующий администратор или IDs менеджеров в `NEGOTIATION_APPROVER_IDS` через запятую. Сотрудники не получают роль администратора ради согласования. Обычные ручные сообщения пока доступны ответственному менеджеру; согласование предложений не является семантическим фильтром всех сообщений.

### Роли и оплата

Тимлид утверждает условия и подбор товаров. Сая координирует доставки и сборщиков Алматы/Астаны. Нина собирает заявки менеджеров на оплату.

Существующий процесс общего файла наличных сохраняется: выгрузка заявок → подача → «Подано» → загрузка оплаченного файла → сопоставление по ID заявки. Не автоматизировать отдельно оговорённый ручной способ оплаты. Подключение ИП-счёта к Bitrix — отдельная ветка, без замены общего файла и без автоматического статуса «Оплачено» после подачи.

## Что реально готово в этом пакете

- Импорт CSV/JSON Apify и `relatedProfiles` с происхождением кандидата, проверкой дублей.
- Настраиваемые задания Apify по ключам; реальный запуск требует task ID, token и лимита расходов.
- Очередь браузерного робота на один Instagram-аккаунт; проверка получателя и аккаунта, скриншоты, ответы вручную из приложения.
- Предложения товара/доплаты, внутренняя экономика, решения тимлида и обращения после согласования.
- Существующая CRM и её финансовая база остаются основой учёта.

## Что пока не считать запущенным

Автоматическое чтение входящих Instagram в структурированную переписку; самостоятельные переговоры Gemini; обход подписок/рекомендаций в живом браузере; push на iPhone; автоматический перенос строго после полного бизнес-согласования в Barter Box. Компактный каталог с поиском подготовлен в изменениях Barter Box; новая форма предложений пока принимает товар/набор вручную и не подключена к каталогу себестоимостей. Решения есть внутри приложения, системных уведомлений телефона пока нет.

Изменения Barter Box поставляются патчем `integration-handoff/barter-box-pilot.patch`: подключение GitHub не разрешило запись в этот репозиторий. Blogery Audit требует отдельного запуска backend и проверки рабочего проекта Supabase. Не применять миграции к случайному проекту по совпадению названия.

## Установка CRM

1. Сохранить резервную копию действующей базы и файлов; зафиксировать рабочую версию для отката. Существующие данные не заменять пустым `db.json`.
2. Развернуть ветку `codex/mixit-connect-pilot` на тестовом сервисе с отдельной копией данных и постоянным диском. Не создавать второй источник производственных записей.
3. Сборка: `cd client && npm ci && npm run build`; затем `cd ../server && npm ci`. Запуск: `node index.js` из `server`.
4. Сохранить действующие настройки авторизации и базы. Установить `DISCOVERY_ENABLED=1`, `BROWSER_ACCOUNT_ID=pilot-instagram`, `INSTAGRAM_BROWSER_WORKER_SECRET`, `BROWSER_SCREENSHOT_DIR` на постоянном приватном диске и `NEGOTIATION_APPROVER_IDS`. Полный пример остальных интеграций — `runtime-configuration.env.example`.
5. Не включать legacy Instagram через Wazzup. Для этого пилота отправку выполняет браузерный worker. WhatsApp подключается отдельно.
6. Открыть HTTPS `/discovery/`, проверить вход менеджера и тимлида, недоступность чужих заданий и приватных скриншотов.

Платный сервер/диск выбирается отдельно; бесплатный эфемерный диск не подходит для базы и сессии. Render-подключение в текущей сессии отсутствует, деплой не выполнен.

## Установка браузерного worker

Нужен постоянно работающий Linux-компьютер/VM с возможностью открыть графический браузер для первоначального входа. Во время обычной работы браузер запускается без окна. Сервер CRM и worker могут быть разными машинами.

1. Установить Node.js 20+, скачать тот же репозиторий в `/opt/mixit/blogger-crm`, создать системного пользователя `mixit` и приватный каталог `/var/lib/mixit/instagram-pilot`.
2. От имени `mixit`: в `instagram-worker` выполнить `npm ci`, установить Chromium через Playwright либо системный Chromium с необходимыми зависимостями.
3. Создать `/etc/mixit/instagram-worker.env` по `deploy/instagram-worker.env.example`, права 600. Секрет worker должен совпадать с CRM; не отправлять его в переписку.
4. В графической сессии того же пользователя с этими переменными выполнить `npm run login`. Владелец вручную проходит вход/2FA. Закрыть браузер.
5. `npm run account` покажет числовой ID аккаунта; записать в `INSTAGRAM_EXPECTED_ACCOUNT_ID`.
6. Установить `deploy/instagram-worker.service` в systemd, выполнить `systemctl daemon-reload`, затем `systemctl enable --now instagram-worker`. Пути в unit должны соответствовать реальной установке.
7. Не запускать два браузера одновременно на одном профиле. Не копировать cookies и профиль в GitHub. При проверке Instagram остановить службу и повторить ручной вход.

## Установка на iPhone

Открыть HTTPS-адрес CRM с `/discovery/` в Safari → «Поделиться» → «На экран Домой» → войти своей учётной записью. Тимлид использует тот же адрес и видит доступные согласования. Интерфейс на телефоне и компьютере работает с одними записями. Для изменений требуется интернет.

## Первый тест

1. Один Instagram-аккаунт и согласованный тестовый получатель. Автопоиск с расходами и массовую очередь пока не включать.
2. Импортировать небольшой обезличенный пример Apify, проверить повторный импорт без дублей.
3. Создать предложение: прайс 100 000; доплата 70 000; себестоимость набора 6 000; доставка 1 000. Расходы должны быть 77 000 ₸. Наценка не увеличивает наши расходы.
4. Проверить отказ, запрос изменений и одобрение тимлидом. Создать обращение только после одобрения.
5. Проверить профиль, точный текст и отправить тестовое сообщение. Убедиться глазами в Instagram, что оно появилось у нужного адресата. Статус `sent_ui` не означает прочтение или API-подтверждение доставки.
6. Проверить просмотр чата и ручной ответ. При `uncertain` сначала проверить переписку, повторно не отправлять вслепую.
7. Только после этого переходить к небольшой вручную проверенной очереди реальных кандидатов.

Остановка: выключить службу worker; не удалять базу, профиль и очередь. Неопределённые отправки перед повторным запуском проверить вручную. Возврат версии CRM выполняется с сохранением базы и совместимости новых записей.

## Дополнение: чтение видимых входящих

Добавлен обработчик видимых сообщений при обновлении чата: проверенный получатель → извлечение строк → запись в `instagram_messages` → показ в приложении. Дедупликация использует аккаунт, блогера и постоянный ID сообщения; одинаковый текст с разными ID не теряется. Входящий ответ меняет контактный статус и отменяет неотправленные стандартные обращения.

Перед активацией на реальном аккаунте нужно проверить DOM и настроить `INSTAGRAM_INCOMING_ROW_SELECTOR`, `INSTAGRAM_MESSAGE_ID_ATTRIBUTE`, `INSTAGRAM_MESSAGE_SENDER_ATTRIBUTE`, `INSTAGRAM_MESSAGE_TEXT_SELECTOR`, при наличии `INSTAGRAM_MESSAGE_TIME_SELECTOR`. Атрибут отправителя должен однозначно давать `incoming` или `outgoing`; если Instagram такого признака не предоставляет, нужен проверенный адаптер его реальной структуры. Произвольные атрибуты выдумывать нельзя. Без подтверждения автора и ID сообщения система сохраняет только скриншот и объяснение, не создаёт фиктивную переписку. Пока чтение запускается обновлением чата; фоновый обход всех диалогов, запросов на переписку, медиа и анализ условий ещё не подключены.

## Windows — первый ноутбук

Установить Node.js LTS 20.12+ (для `--env-file`) с nodejs.org, скачать ZIP ветки PR и распаковать. Открыть PowerShell в `instagram-worker/windows`, выполнить `powershell -ExecutionPolicy Bypass -File .\setup.ps1` (ограничение обходится только для этого запуска скрипта, постоянная политика не меняется). Установщик загружает npm-зависимости и Chromium; администратора обычно не требует.

В созданном `instagram-worker/.env.local` указать HTTPS-адрес уже развёрнутой CRM, имя аккаунта и общий секрет. Запустить `windows/login.cmd`, вручную войти в Instagram и закрыть браузер. Запустить `windows/account.cmd`, записать числовой ID в `.env.local`. Запустить `windows/start.cmd` и оставить окно работающим. Закрытие окна останавливает робота. Не запускать одновременно два окна. Профиль хранится вне папки проекта, в `%LOCALAPPDATA%\MIXIT\instagram-pilot`. Для теста ноутбук должен оставаться включённым и не переходить в сон. Телефоны работают с публичным HTTPS-адресом CRM, а не с адресом ноутбука.

После настройки и проверки адаптера чтения можно включить на CRM `INSTAGRAM_AUTO_READ_ENABLED=1`; `INSTAGRAM_AUTO_READ_INTERVAL_MS` по умолчанию 300000. Фоновая проверка обслуживает только контакты, которым этот робот уже отправил сообщение; проверяет по одному диалогу при свободной очереди. Это не обход неизвестных запросов Direct и не гарантия полной истории. При выключенном ноутбуке проверка приостанавливается.

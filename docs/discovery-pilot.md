# MIXIT Connect: коммуникация с блогерами

Пилот использует **существующую Blogger CRM**, таблицу `bloggers`, текущие входы сотрудников и сохранённые ID. Второй рабочей базы нет. Выключен по умолчанию: `DISCOVERY_ENABLED=1` включает новые маршруты.

## Приложение

Открыть `/discovery/` на домене CRM с компьютера или iPhone. Используется текущий логин/пароль. В Safari: «Поделиться» → «На экран Домой». Для работы с другого телефона все открывают один HTTPS-сервер CRM. Функции: список блогеров, поиск, мои кандидаты, закрепление за менеджером, готовые обращения, копирование текста, открытие Instagram и подтверждение реальной ручной отправки. Это PWA-оболочка коммуникации, не автоматический Instagram-клиент.

Заявки и сборка остаются в компьютерном Barter Box. Координатор доставок — Сая; выбор товаров и подсчёт себестоимости доступны каждому менеджеру в основной форме Barter Box, отдельный PR.

## Apify и рекомендации

В приложении загрузить CSV/JSON → проверить → импортировать. Поддержаны username, profileUrl/url, fullName, followersCount. Пример ниже вымышленный:

```json
[{"username":"demo_beauty","fullName":"DEMO","followersCount":1000,"relatedProfiles":[{"username":"demo_related","id":"sample-42"}]}]
```

`relatedProfiles` из реальной выгрузки расширяет подбор: каждый кандидат сохраняет источник и seed-профиль. Для CSV вложенное поле должно быть JSON-строкой. Бесконечного обхода рекомендаций нет, до 100 рекомендаций на исходную строку и до 5000 строк всего. Рекомендации, которых нет в данных, не выдумываются. Проверка географии аудитории, качества контента и тематического соответствия остаётся отдельной задачей.

Дубли проверяются по нормализованному Instagram-нику и ID площадки, если он доступен. Существующие статусы, цены, ответственные и история не перезаписываются. Новый блогер получает new/unreviewed, без автоматического закрепления. Сопоставление сменившего ник аккаунта со старой записью без ID требует ручной проверки.

## Коммуникация

Кандидат → «Взять в работу» → «Подготовить сообщение» → проверить текст → копировать → открыть профиль → отправить → «Я отправил(а)». При ответе/отказе неподтверждённые черновики отменяются. У другого сотрудника блогер повторно не забирается. Администратор сохраняет прежний процесс распределения.

Автоматическая отправка Direct, чтение ответов, Muse, скриншоты телефона и персональная ИИ-генерация не подключены. Черновик — редактируемый шаблон, не результат изучения профиля. API не объявляет сообщение отправленным по факту создания черновика.

## Автозагрузка готовой выгрузки

`tools/apify_sync.py` загружает существующий Apify dataset и делает preview в CRM. Нужны секреты `APIFY_TOKEN`, `MIXIT_CRM_TOKEN` и HTTPS `MIXIT_CRM_URL` через окружение. Токен CRM — действующий авторизованный токен, его срок нужно учитывать. Для регулярного процесса лучше отдельный ограниченный сервисный доступ после согласования.

```sh
python tools/apify_sync.py --dataset-id YOUR_DATASET_ID --include-related
python tools/apify_sync.py --dataset-id YOUR_DATASET_ID --include-related --commit
```

Вторая команда пишет только после успешной проверки. Скрипт **не запускает платный Actor**, не создаёт расписание и не отправляет сообщения. Настройка регулярного поиска по ключам требует выбора фактического Actor/input, лимита бюджета и защищённого доступа.

## API

- `POST /api/discovery/import`: content, format=csv/json, includeRelated, dryRun. По умолчанию preview.
- `POST /api/discovery/claim`: id существующего блогера.
- `POST /api/discovery/draft`: blogger_id, text.
- `GET /api/discovery/outbox`: свои черновики; администратору — все.
- `POST /api/discovery/draft-sent`: id черновика, ручное подтверждение.
- `POST /api/discovery/contact-status`: id, status, note, follow_up для later.

Права новых изменяющих маршрутов — admin/manager, текущие read-only/operator ограничения сохраняются. Старые маршруты не заменены. Новые данные сохраняются штатным lowdb в той же БД; Supabase-синхронизация существующих зеркал не изменяется. Возникающие конфликты при работе нескольких экземпляров сервера требуют общей БД: этот пилот рассчитан на существующий однопроцессный lowdb-сервер.

## Проверка и запуск

```sh
cd server
npm ci
node --test test/discovery.test.js test/discovery-http.test.js
```

Сначала backup db.json и тестовая копия. Новые API и синтаксис проверены; браузерная QA и физический iPhone не проверены. Файл товаров и реальные цены в публичный репозиторий не добавлены. Prod-деплой не выполнялся.

# Заявка → существующая CRM → проверенный счёт ИП → Bitrix

1. Barter Box создаёт связанную заявку в **существующей таблице payments Blogger CRM**. При подтверждении записи получает её CRM ID. Если CRM недоступна, интерфейс сообщает об очереди, а не об уже созданной записи.
2. В старой таблице CRM рядом с существующей ссылкой согласования добавлено «Прикрепить счёт ИП». Сотрудник прикладывает файл и подтверждает, что получен и проверен счёт именно на сумму заявки. Без счёта запись остаётся в CRM.
3. Файл сохраняется на постоянном закрытом диске; в CRM — ссылка на внутренний файл, контрольная сумма, проверивший сотрудник и время. Большой PDF не кладётся в db.json.
4. Сервер вызывает действующий REST-вебхук Bitrix **только для заданного объекта «Согласование оплаты»** и прикладывает сам файл в Base64, а не только URL.
5. Один внешний ID CRM → один элемент. Перед созданием проверяется существующий элемент по отдельному полю externalKey. После сетевой неопределённости требуется сверка, автоматического второго элемента нет.
6. Передано в Bitrix не означает оплачено. Фактический статус и чеки задаются текущим процессом CRM и возвращаются в Barter Box.

Для наличных этот маршрут не применяется. Старый реестр не заменяется.

## Настройки

`BITRIX_PAYMENT_ENABLED=1` включает worker после настройки. `BITRIX_PAYMENT_WEBHOOK_BASE` — защищённый base URL действующего REST-вебхука вида `https://<портал>/rest/<user>/<secret>/`; **не присылать его в чат и не коммитить**.

`BITRIX_PAYMENT_DESTINATION=Согласование оплаты` подтверждает выбранный рабочий процесс. Автоматически определять тип вкладки по названию нельзя:

- `BITRIX_PAYMENT_OBJECT=smart`: существующий смарт-процесс; `BITRIX_PAYMENT_PARAMS_JSON` содержит точный `entityTypeId` и при необходимости categoryId.
- `BITRIX_PAYMENT_OBJECT=list`: существующий список; params содержит точные `IBLOCK_TYPE_ID` и `IBLOCK_ID`.

`BITRIX_PAYMENT_FIELDS_JSON` сопоставляет семантику с **реальными** полями вашего процесса: `invoice`, `externalKey`, `amount`, `recipient`; дополнительно `title`, `manager`, `reason`. Для smart имя поля файла передаёт пару [имя, Base64]; для list — соответствующее свойство файла. Реквизиты и ID не угадываются. Метод создания обычных задач не используется.

Сначала нужно прочитать действующую схему и сверить её с настройками. В исходниках точного webhook/ID полей нет, поэтому рабочее подключение не заявляется. Проверки используют имитацию REST-ответов; реальная выплата и реальный элемент Bitrix не создавались.

Документация формата файлов: https://apidocs.bitrix24.com/api-reference/files/how-to-upload-files.html
